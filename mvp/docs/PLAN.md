# S#5·6 태블릿 ↔ XR뷰 연동 MVP — 10일 플랜 (수정본)

최초 작성 2026-10-02 · 수정 2026-10-05
원본: `MVP 10일 플랜.md`(업로드본). 이 문서는 진행하면서 바뀐 결정을 반영한 최신판이다. 실행 방법은 [`README.md`](../README.md).

## 가정

- 전시장에 헤드셋은 없다. 아이맥 화면이 "소비자가 헤드셋으로 보는 시야(XR뷰)"를 대신한다.
- 관람객은 태블릿을 든 매니저 역할로 체험한다.
- **테스트는 항상 맥북**(서버 + XR 화면 Chrome), 전시는 아이맥 24". 렌더는 윈도우 PC(D5)에서 한다.
- 1인 작업, 하루 6~8시간.

## 1. 핵심 구조

```
[아이패드 Safari /tablet] ──WebSocket──▶ [맥북·아이맥 Node 서버 :3000] ──WebSocket──▶ [Chrome /xr 전체화면]
                                          └ 상태 1개 보관 · 접속/재접속 때 전체 스냅샷 · 인터넷 불필요
```

- D5로 360° 파노라마를 렌더하고, 두 화면이 같은 파노라마를 **각자 다른 방향으로** 본다(미러링 아님).
- **배경 고정 + 레이어(A안)**: 시점마다 기본 배경 1장을 깔고, 아일랜드·바닥재는 **직접 딴 누끼 레이어**로 겹친다. XR 서비스의 "스캔한 공간은 그대로, 그 위에 오브제·자재를 올려 본다"를 그대로 보여주기 위해서다.
- 주석은 화면 좌표가 아니라 **방향(yaw·pitch) + 그린 시점**으로 저장한다. 태블릿에서 그린 선이 XR뷰의 같은 벽 위치에 붙는다.

## 5. 렌더 계획

- 파일 이름·목록·카메라 규칙: [`assets/pano/README.md`](../assets/pano/README.md)
- 시점 2곳(정면 v1, 측면 v2) × 시점당 13장(아일랜드 없음 1 + 아일랜드 3 × 바닥 4).
- **8K만 렌더**해서 JPG로 저장. 옵션 장면(아일랜드·바닥재)은 **누끼 PNG**(`이름_cut.png`, 원본과 같은 크기)도 만든다.
- 맥북에서 `git pull` → `npm run pano:prep` → 4K와 누끼 레이어가 `built/`에 자동 생성.
- 8K에서 GPU가 버티지 못하면 6K(6144×3072)도 동작한다(아이맥에서 약간 덜 선명). ⚠️검증 필요
- **JPG와 누끼만 GitHub에 올린다**(웹 업로드 한 장 25MB 이하). 원본 PNG는 렌더 PC에만 둔다. 맥북 용량 보호.
- 누끼 장수: 시점당 아일랜드 3 + 바닥재 9 = 12장. 바닥재 누끼는 바닥 영역만.

우선순위
1. 측면: 기본 배경, 아일랜드 2, 아일랜드 2 + 바닥재 B (60초 스크립트 그대로)
2. 정면: 같은 3장
3. 나머지 아일랜드·바닥재 조합

## 7. 리스크

- **전시장 와이파이 기기 간 차단(AP isolation)** → 인터넷 없는 트래블 라우터에 두 기기만 연결.
- **렌더 간 카메라·노출 차이** → 누끼가 배경과 어긋나거나 떠 보인다. 같은 시점은 카메라 고정, D5 노출 수동 고정.
- **누끼 작업량**(시점당 최대 12장) → 시나리오 조합(아일랜드 2, 바닥재 B)부터. 밀리면 나머지는 통째 교체로 둔다.
- **저장소 용량**: 8K JPG 한 장 수 MB~십수 MB × 26장 → 수백 MB. GitHub 권장 범위 안이지만 재렌더가 많으면 커진다 ⚠️검증 필요. 커지면 Git LFS 검토.
- **아이패드 Safari 텍스처 메모리** → 태블릿은 4K, 레이어는 잘라낸 크기만 올린다. 실기기에서 1~2분 둘러보기로 확인. ⚠️검증 필요
- **D5 8K 렌더 부하**(GPU 다운 경험) → 6K로 낮추거나 야간 배치 렌더.
- **iOS 자이로 둘러보기**는 HTTPS·권한 필요 → MVP는 드래그로.
- 최후 백업: 전체 시연을 화면 녹화해 아이맥에서 루프 재생.
